# 100MON の問題づくり

TV で問題文が1文字ずつ出る、4択の速読クイズ。日本語と英語で**同じ100問**を出し、ランキングは言語別（design.md §7）。

## 決まりの正本

迷ったら、次のファイルが正しい。このページはその要点と、人の確認で分かったことのまとめ。

| 中身 | 場所 |
|---|---|
| 問題の条件・書き方（生成役に渡す指示そのもの） | `pipeline/generate_period.py` の `build_prompt` と `STYLE_RULES` |
| 機械で弾く形式チェック | 同じファイルの `local_check` |
| 難易度の基準 | `pipeline/test_generators.py` の `DIFF_GUIDE` と `CALIBRATION` |
| 検証のチェック項目・配分・流れ | `design.md` §8 |

**決まりを変えるときは、先に `generate_period.py` を直し、そのあとこのページを直す。** 生成役のモデルが読むのは `generate_period.py` だけなので、ここだけ直しても次の生成には効かない。

## 1問ずつ確かめること

### 正解が1つに決まるか
- 事実として確定していて、時期で変わらない（現職の人、最新の記録、統計の順位は使わない）
- 数え方の揺れを、言い方そのもので絞る。P01 で直した例：
  - 永久歯の本数：親知らずを数えない 28本 も正しいので、選択肢から 28本 を外した
  - 試合の人数：控えを含むと変わるので「コートに出る人数」「フィールドに出る人数」にした
  - 一番大きい臓器：皮膚も臓器に数える考えがあるので「内臓」にした
- 正解以外の選択肢も当てはまらないか確かめる（「音より速い速度」の案は「光速」も当てはまり不採用）
- 法律や公式の定めが無いもの（国花・国鳥など）を、定まっているように問わない

### 日本語と英語で同じ知識を問うか
- **片方の言語でしか成り立たない問題は作らない。** 「英語で『犬』は？」は英語版だと「日本語の inu はどれか」になり、日本語の知識が要る別の問題になる。P01 では「猫」「ありがとう」「犬」の3問をこの理由で差し替えた
- ラテン語のように、どちらの話者にとっても外国語のものはよい
- 日本の事柄を問う問題（五十音、漢字、「パン」の語源）はよい。英語版でも同じ知識を問うから
- 英語版の問題文に正解の語が出てしまわないか（例：braille の考案者 → Braille）
- 英語版も直訳でなく自然な英語にする。疑問符は付けない

### 書き方（日本語）
- 10〜25文字が目安。句点は付けない。「〜ですか」「〜でしょう」にしない
- 見出しとして読めるものは名詞で終える（「日本で一番高い山」）。「何」「いくつ」で尋ねるもの、名前・呼び方を問うものは全角の「？」で終える（「1ダースはいくつ？」）
- 直訳調にしない：「〜の名前」「〜の目安」「〜を意味する単語」「日本語の〜」
- かっこの断り書きを足さない。言い方そのもので意味を1つに絞る
- 本の題名は『』、曲・絵・映画の題名は「」

### 選択肢
- 単語か短い語句。日英で正解の位置（answerIndex）は共通。正解の位置は問題ごとにばらけさせる
- 不正解の3つは、確実に不正解で同じ種類のもの（すべて山の名前、など）
- 同じ種類でそろえて最後まで読ませる問題と、そろえずに早く決まる問題を混ぜる

### 重複と同じ型
- 同じ題材・同じ正解を2回使わない（過去のピリオドも含む。`load_used_from_data`）
- 同じ型を増やさない。P01 で重なった型：元素記号から元素を答える（4問）、「〜を作曲した作曲家」、英語の単語を答える
- 言い回し違いの重複は `text_keys` で捕まえる（「ピアノの鍵盤の数」と「ピアノの鍵盤の数（標準的なもの）」がすり抜けたことがある）

## 100問のそろえ方

- 難易度（通常週）：最初級 25、初級 30、中級 20、上級 25。上級は「物知りなら普通に知っている」水準
- **使い回し**：通常週の100問のうち 25% は過去の通常週の問題を元の ID のまま入れる（`generate_period.py` が自動で選ぶ。`config.PROD_REUSE_RATIO`）。直前の週と激ムズウィークの問題は使わない。過去の通常週が足りないうち（P02 まで）は0問
- 答えが決まる位置（decisionPoint）は言語ごとに分布を見る。1文字目で決まる問題が多いのは、選択肢が雑という信号
- 分野は偏らせない

## 作業の手順

### 新しいピリオドを作る
```sh
# boto3 が入っている Python はこれ。途中で落ちたら --resume、試すだけなら --dry-run N（data/ を触らない）
~/anaconda3/bin/python3 pipeline/generate_period.py --period-id 2026-P02 \
    --starts 2026-10-26T00:00:00Z --ends 2026-11-02T00:00:00Z --quarter 1
```
生成のあと、人の目で `pipeline/reports/<period>/questions.md` を確かめる（★は検証で一度落ちたもの）。

### エキシビジョンの問題を毎月作り直す
エキシビジョン（記録に残らないモード）は、アプリに入れた「今月の既定の問題」と、終わったピリオドの問題から出す。既定の問題は毎月作り直す。
```sh
# 初級（最初級50＋初級50）・中級100・上級100（config.EXHIBITION_ALLOCATION）
~/anaconda3/bin/python3 pipeline/generate_period.py --exhibition --period-id exhibition-2026-11
# 激ムズ100問は Claude が pipeline/written/exhibition-2026-11-hell.json に書いて、検証に通す
~/anaconda3/bin/python3 pipeline/import_written.py --set-id exhibition-2026-11-hell --check-only
~/anaconda3/bin/python3 pipeline/import_written.py --set-id exhibition-2026-11-hell
```
- **生成役（Opus 4.6）には1日のトークン上限がある**。300問を1日で作り切れず「Too many tokens per day」で止まることがある（2026-10-16 は285問で止まった）。採用済みは `reports/<id>/accepted.json` に残るので、その日は `--resume --no-generate` で採用済みだけ書き出し、翌日 `--resume` で残りを作る。激ムズの検証（Mistral・Qwen）を同時に流すと混みやすいので、生成とは時間をずらす
- 終わったら `app/src/data.ts` の `EXHIBITION_SETS` の読み込み先を新しい月のファイルに替える。古い月のファイルは data/ に残す（生成役が使用済みとして読み、あとの週とかぶらないように）
- 合格しなかった激ムズの問題は `reports/<set-id>/written.md` に理由が出る。直して流し直す（合格済みは検証し直さない）

### 激ムズの問題を書く（エキシビジョン・激ムズウィーク）
- 水準は設計書の付録A「ヘルモード」：正解を見れば納得できるが、その場では出てこない。知識そのものが難しく、書き方は素直に
- **上級どまりになりやすい**（2026-10-16、最初に書いた100問をオーナーが「上級位じゃない？」と指摘して書き直した）。1問ずつ次で点検する
  - 物知りがその場で答えられる「有名な人物・作品・場所を当てる」問題は上級。例：電子を発見した人、ルーヴルのピラミッドの設計者、ハムレットの舞台、ナポレオンが亡くなった島
  - 激ムズは、理屈や仕組みで差がつく（光合成の酸素は水から、季節は地軸の傾き、金星が一番熱い）か、思い込みの逆を突く（アフリカ最南端はアガラス岬、南米の最高峰はアコンカグア）
  - 不正解の3つを、同じ分野のよく知られた言葉でそろえる（三世一身法の723年と墾田永年私財法の743年、ヘルツの415・432・440・466）
- `test_generators.py` の `CALIBRATION` にある見本の問題と、その言い換えは使わない
- 諸説ある話・「〜とされる」で逃げる話は避ける。検証では「信頼できる資料で確かめられる事実か」の項目が足される（`import_written.py`）
- 正解は先頭に書いて、書き出すときに正解の位置を 0〜3 に均等に割り振ると楽

### 人の確認で直す・差し替える
`pipeline/revisions/<period>.json` に書き足して、`revise_period.py` を流す。書き方はファイル先頭の説明どおり。
```sh
~/anaconda3/bin/python3 pipeline/revise_period.py --period-id 2026-P01 --check-only   # 形式チェックだけ
~/anaconda3/bin/python3 pipeline/revise_period.py --period-id 2026-P01                # 検証 → 確定位置 → 書き出し
```
- 生成役に差し替えさせると、同じ型を出してくることがある。型を避けたいときは、人が問題を書いて `"replace": true` に中身を付ける（検証だけ通る）
- **落とし穴1**：選択肢だけを直した項目は問題文が同じなので、流すたびに「まだ済んでいない」と見なされ、確定位置が測り直されて値がぶれる。流したあと `git diff data/` で、直していない問題の値が動いていないか見て、動いていたら戻す
- **落とし穴2**：`reports/<period>/revisions.md` と `revisions.json` は、流すたびにその回の分だけで上書きされる。2回目以降は前の内容を残して、その回の分を書き足す（P01 の2回目は `revisions.json` の `later_runs` に入れた）
- **使い回した問題は直さない**：ID が別のピリオドのものは `revise_period.py` が止める。中身がおかしければ元のピリオドで直す

### サーバーに入れる・アプリに入れる
- サーバー：`backend/README.md` の手順で `npm run backend:seed`。本番のデータを書き換えるので、**オーナーに確かめてから**
- アプリは問題ファイルをビルド時に取り込む。直したら作り直す
  - Fire OS 版：`cd fos && npm run tv`（`fos/README.md`）
  - Vega 版：`cd app && npm run sim`

## オーナーの決定

- 2026-P01 は、名詞で終わる問題が多くてもこのままにする（2026-10-16）。次のピリオドを作る前に、問いかけの形（「〜は？」）に寄せるかをオーナーに一度確かめる
- 激ムズウィークの最初の2回（第12ピリオド 2027-01-04〜、第24ピリオド 2027-03-29〜）は、Bedrock を使わず Claude Code の Claude が書く（2026-10-16）。書いたものも検証1・検証2に通し、設計書の激ムズ用の追加チェックを守り、人の確認を厚くする。期間のデータには isHardWeek・猶予10秒・挑戦2回・60分を入れる。第36ピリオド以降の生成役は、その時点の Bedrock の開放状況で決める
